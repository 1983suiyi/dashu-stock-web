# 大数选股工具 · 账号与多用户数据方案

> 状态：**历史方案与决策背景；账号、多用户同步和管理端已实现**
> 当前实现细节以 [README](../README.md) 和 [技术方案](技术方案.md) 为准；本文件中的“待确认/待开始”内容保留作决策记录，不代表当前阻塞项。

> 适用范围：把当前「单用户、数据存浏览器」的工具，改造为「外网部署、多账号、每人数据隔离」的服务。

## 0. 背景与目标

### 0.1 现状

| 维度 | 当前实现 |
| --- | --- |
| 用户 | 单用户，无账号 |
| 数据 | 全部存浏览器 `localStorage`，共 9 个 key |
| 服务端 | 零第三方依赖的 `node:http` 服务（`server/index.mjs`），**无状态**，只做行情代理与静态托管 |
| 部署 | `npm start` 单进程提供接口 + 静态站点 |

### 0.2 目标

1. 外网部署，**多用户**各自登录。
2. 每人的持仓、资金、归档、市场记录**互相隔离**，换设备/换浏览器可恢复。
3. 尽量延续「轻量、少依赖、数据驱动」的既有风格。

### 0.3 硬约束

- 手机号属个人信息（《个人信息保护法》），需加密存储、脱敏展示、提供注销入口。
- 服务端当前零第三方依赖；本次是否打破，见 [第 3.1 节](#31-sqlite-选型)（有「保持零依赖」的路径）。
- 不改动与账号无关的核心业务逻辑（评分、选股、组合、仓位口径一律不动）。

## 1. 验证码方案（已决策：**邮箱验证码**）

### 1.1 为什么暂时不用短信（调研结论，2026-11 核实）

| 方案 | 免费情况 | 硬门槛 |
| --- | --- | --- |
| 腾讯云短信 | 企业认证「首次开通有奖」自 **2026-03-24** 起降为 **200 条** | **自 2025-09-18 起，个人认证不再支持创建「个人自用签名」**，只能用需企事业单位资质的「他用签名」 |
| 阿里云短信 | **不支持直接申请免费测试短信**，仅新用户活动可领 | 签名需资质证件 + 实名报备审核 |
| MobTech SMSSDK | 老牌「免费短信验证码」，新用户接入秒验送 **1000 条**（以金额充入、不可提现） | 主要面向 App SDK；有每日 20 条等限制；活动仅限中国大陆 |
| Twilio | **30 天试用**，含约 100 条 SMS | 试用期**只能发给已验证号码（最多 5 个）**，短信带 `Sent from your Twilio trial account` 前缀；无永久免费层 |

**结论**：长期免费且可用的短信通道基本不存在；国内真正的卡点是**签名资质**——个人开发者拿不到签名，付费也发不出去。因此内测阶段改用邮箱验证码。

### 1.2 邮箱验证码选型

| 服务 | 免费额度 | 备注 |
| --- | --- | --- |
| **Brevo**（原 Sendinblue） | **300 封/天（≈9000/月），永久免费** | 支持 SMTP / REST API，国内可接入、送达率高（首选） |
| Resend | 3000 封/月（每天上限 100） | 开发者体验好（备用） |
| Elastic Email | 3000 封/月 | 备用 |

- 需要**自有域名**配置 SPF / DKIM / DMARC 才能保证送达率；无域名可先用服务商默认发件域（易进垃圾箱，仅够内测）。
- 发信通道做成**可插拔**（见 1.3），避免以后切短信时改动业务代码。

> **决策**：默认发信通道 = **Brevo**（Resend 备用）。是否已有自有域名待确认（见第 10 节）。

### 1.3 通道抽象（为将来切短信预留）

```
VerificationChannel (抽象)
├── EmailChannel   → Brevo / Resend      （本期实现）
└── SmsChannel     → 阿里云 / 腾讯云 / Mob（预留，上线有资质后再接）
```

业务层只调用 `sendCode(target, purpose)` 与 `verifyCode(target, purpose, code)`，**不关心底层是邮件还是短信**。这样从邮箱切到短信时，只替换一个 channel 实现。

## 3. 数据与存储

### 3.1 SQLite 选型

当前项目服务端**零第三方依赖**。SQLite 有两条路径：

| 方案 | 依赖 | 说明 |
| --- | --- | --- |
| **Node 内置 `node:sqlite`**（✅ **已选定**） | **无**（0 依赖） | `v22.5.0` 引入；`v22.13.0 / v23.4.0` 起**不再需要 `--experimental-sqlite` flag**；`v24.15.0` 起为 **Release Candidate**。API 为同步的 `DatabaseSync` / `StatementSync` |
| `better-sqlite3` | 原生模块（需编译/预编译） | 生态成熟，但会打破零依赖、且外网部署需匹配平台二进制 |

> 本机实测：Node **v22.3.0**，`node:sqlite` **不可用**（`ERR_UNKNOWN_BUILTIN_MODULE`）。
> **决策：采用内置 `node:sqlite` 以保持零依赖**；需将 Node 升级到 **≥ 22.13**（免 flag），推荐 **≥ 24.15**（RC，更稳）。升级方式待确认（见第 10 节）。

### 3.2 表结构

```sql
-- 用户
CREATE TABLE IF NOT EXISTS users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  email         TEXT    NOT NULL UNIQUE,        -- 主登录标识
  phone         TEXT    UNIQUE,                 -- 可选，号码回收风险，不作唯一登录名
  password_hash TEXT    NOT NULL,               -- scrypt 派生
  password_salt TEXT    NOT NULL,
  status        TEXT    NOT NULL DEFAULT 'active',  -- active / disabled
  role          TEXT    NOT NULL DEFAULT 'user',    -- user / admin（管理端权限依据）
  created_at    INTEGER NOT NULL,
  last_login_at INTEGER
);

-- 验证码（邮箱/短信统一）
CREATE TABLE IF NOT EXISTS verification_codes (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  target      TEXT    NOT NULL,   -- 邮箱地址
  channel     TEXT    NOT NULL,   -- email / sms
  purpose     TEXT    NOT NULL,   -- register / login / reset
  code_hash   TEXT    NOT NULL,   -- 不存明文
  expires_at  INTEGER NOT NULL,
  consumed_at INTEGER,
  attempts    INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_codes_target ON verification_codes(target, purpose, created_at);

-- 会话
CREATE TABLE IF NOT EXISTS sessions (
  token_hash  TEXT    PRIMARY KEY,   -- sha256(token)，不存明文 token
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER NOT NULL,
  last_seen_at INTEGER,
  ip          TEXT,
  user_agent  TEXT
);

-- 用户业务数据（通用 KV：一种 kind 存一块 JSON）
CREATE TABLE IF NOT EXISTS user_data (
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  kind       TEXT    NOT NULL,        -- holdings / cash / totalAssets / capitalEvents / archives
  payload    TEXT    NOT NULL,        -- JSON 字符串
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, kind)
);

-- 市场温度（公共，全站共用一份；按日期一行）
CREATE TABLE IF NOT EXISTS market_temperature (
  date            TEXT    PRIMARY KEY,   -- 形如 2026-11-19
  index_level     REAL,
  exposure_pct    REAL,
  pb_median       REAL,
  pe_median       REAL,
  below_net_count INTEGER,
  three_low_count INTEGER,
  risk_passed_count INTEGER,
  updated_at      INTEGER NOT NULL
);

-- 限流
CREATE TABLE IF NOT EXISTS rate_limits (
  key          TEXT    NOT NULL,      -- 如 code:send:邮箱、login:ip:1.2.3.4
  window_start INTEGER NOT NULL,
  count        INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (key, window_start)
);

-- 邀请码（注册白名单）
CREATE TABLE IF NOT EXISTS invites (
  code       TEXT    PRIMARY KEY,          -- 邀请码
  created_by INTEGER REFERENCES users(id), -- 生成的 admin
  max_uses   INTEGER NOT NULL DEFAULT 1,   -- 可用次数
  used_count INTEGER NOT NULL DEFAULT 0,
  expires_at INTEGER,                      -- 为空表示不过期
  status     TEXT    NOT NULL DEFAULT 'active',  -- active / revoked
  created_at INTEGER NOT NULL
);

-- 审计日志（登录与管理操作）
CREATE TABLE IF NOT EXISTS audit_logs (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  actor_user_id INTEGER REFERENCES users(id),  -- 操作者
  action        TEXT    NOT NULL,              -- login / login_failed / invite_create / user_disable / ...
  target        TEXT,                          -- 被操作对象（用户 id / 邀请码 / 日期）
  detail        TEXT,                          -- JSON 附加信息
  ip            TEXT,
  created_at    INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_audit_created ON audit_logs(created_at);
```

**为什么 `user_data` 用通用 KV 而不是拆多表**：现有客户端本来就是「整块 JSON 存一个 localStorage key」，用 KV 保持**语义等价**，迁移与同步成本最低，也不会因表结构差异引入口径变化。后续若需要按字段查询/统计，再单独抽出明细表。

## 4. 鉴权与安全

| 项 | 方案 |
| --- | --- |
| 密码 | `crypto.scrypt` + 每用户随机盐；校验用 `crypto.timingSafeEqual` 常数时间比较 |
| 会话 | 服务端生成 32 字节随机 token，**只存 `sha256(token)`**；前端拿 `HttpOnly + Secure + SameSite=Lax` Cookie |
| 登录标识 | **邮箱为主**；手机号仅作可选绑定 + 找回，避免号码回收导致账号被接管 |
| 验证码 | 6 位数字，哈希存储，**5 分钟有效、单次消费**，最多校验 5 次即作废 |
| 发送限流 | 同一目标 60 秒一次、每日上限（如 10 条）；同 IP 每日上限；超限返回 429 |
| 防轰炸 | 注册/找回前置「邀请码」（见 9.1） |
| CSRF | 写操作要求自定义头（如 `X-Requested-With`）+ `SameSite=Lax` |
| 传输 | 生产必须 HTTPS（Secure Cookie 依赖 HTTPS） |
| 管理端防护 | 仅 `role=admin`；建议再叠加管理员邮箱白名单 + 强制二次验证；所有写操作记入 `audit_logs` |

## 5. 接口设计

统一响应：成功 `{ ok: true, data }`；失败 `{ ok: false, error: { code, message } }`。

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/auth/send-code` | 否 | body `{ email, purpose }`，发送验证码 |
| POST | `/api/auth/register` | 否 | body `{ email, code, password }` |
| POST | `/api/auth/login` | 否 | body `{ email, password }`，成功置 Cookie |
| POST | `/api/auth/logout` | 是 | 清除当前会话 |
| GET | `/api/auth/me` | 是 | 返回当前用户信息 |
| POST | `/api/auth/reset-password` | 否 | body `{ email, code, newPassword }` |
| GET | `/api/user-data/:kind` | 是 | 读取某类用户数据 |
| PUT | `/api/user-data/:kind` | 是 | 覆盖写入某类用户数据（带 `updated_at`） |
| GET | `/api/market-temperature` | 是 | 读取**公共**市场温度（按日期倒序，最多 N 条） |
| POST | `/api/market-temperature` | 是 | 按日期**幂等 upsert** 当日一条（公共，任意登录用户写入同一份） |

**管理端接口**（前缀 `/api/admin/*`，每个接口强制 `role=admin`，否则返回 403）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/invites` | 邀请码列表 |
| POST | `/api/admin/invites` | 生成邀请码（可设次数、有效期） |
| PATCH | `/api/admin/invites/:code` | 失效 / 恢复邀请码 |
| GET | `/api/admin/users` | 用户列表（分页、支持按邮箱/状态筛选） |
| PATCH | `/api/admin/users/:id` | 禁用 / 启用用户 |
| DELETE | `/api/admin/users/:id` | 删除用户（级联清理其 `user_data` / `sessions`） |
| POST | `/api/admin/users/:id/reset-password` | 重置指定用户密码 |
| PUT | `/api/admin/market-temperature/:date` | 校正指定日期的公共市场温度 |
| GET | `/api/admin/audit-logs` | 审计日志（分页） |

> 管理端**写操作一律记入 `audit_logs`**；用户列表返回邮箱时**脱敏**（如 `a***@qq.com`），完整值仅在有明确需要时单独接口返回并记录审计。

错误码：`INVALID_EMAIL` / `CODE_EXPIRED` / `CODE_MISMATCH` / `RATE_LIMITED` / `EMAIL_TAKEN` / `BAD_CREDENTIALS` / `UNAUTHORIZED` / `FORBIDDEN` / `INVALID_INVITE` / `INVALID_INPUT`。

## 6. 数据迁移（localStorage → 云端）

### 6.1 key 分类

| 归属 | localStorage key | 处理 |
| --- | --- | --- |
| **用户私有** | `dashu-user-holdings`（持仓） | 迁移到 `user_data.kind=holdings` |
| | `dashu-cash-balance`（现金） | → `cash` |
| | `dashu-total-assets`（总资产） | → `totalAssets` |
| | `dashu-capital-events`（资金流水） | → `capitalEvents` |
| | `dashu-workspace-archives`（归档） | → `archives` |
| **公共（不进用户私有）** | `dashu-market-temperature`（市场温度） | **公共表** `market_temperature`，全站共用（见 6.3） |
| **公共缓存** | `dashu-market-cache`（全市场当天缓存） | 不按用户存，保持本地/改服务端统一缓存 |
| | `dashu-daily-kline-cache`（日频 K 线） | 同上 |
| | `dashu-index-snapshot`（指数快照） | 同上 |

### 6.2 迁移方式

1. 用户首次登录成功后，前端检测到本地仍存在**用户私有** key → 弹「是否把本地数据导入账号？（只会执行一次）」。
2. 确认后逐 kind `PUT /api/user-data/:kind`；成功后打标记 `dashu-migrated:<userId>`，避免重复导入。
3. 日常读写：**先写本地缓存（离线可用），再异步同步云端**；登录时以服务端为准拉取覆盖本地。
4. 冲突：以 `updated_at` 较新者为准（最后写入胜出）；本期不做复杂合并。

### 6.3 关于「市场温度」的特别说明

`dashu-market-temperature` 的字段（上证点位、PE/PB 中位、破净数、三低命中数）本质是**公共市场数据**，按用户各存一份会重复且互相不一致。

> **决策：公共化**。改为服务端 `market_temperature` 表统一记录，所有用户读同一份；写入按日期**幂等 upsert**。
> 本地那份 `dashu-market-temperature` 仅作离线缓存，不再作为「用户私有数据」上云。

## 9. 分阶段实施计划

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| **P1 登录鉴权闭环** | 邮箱验证码 + 注册（**需邀请码**）/ 登录 / 找回 + 会话中间件；**管理端入口 + 邀请码管理**；业务数据仍留 `localStorage` | 可注册、可登录、刷新保持登录、可退出；无邀请码不能注册；非 admin 访问 `/api/admin/*` 返回 403 |
| **P2 用户数据云端化** | `user_data` 读写接口 + 本地数据一次性迁移 + 前端同步层；**管理端：用户管理 + 市场温度校正** | 换浏览器/设备登录后持仓与资金完整恢复；管理端可禁用用户、校正温度 |
| **P3 安全加固与上线** | 限流、**审计日志**、注销、备份、HTTPS、隐私政策 | 通过限流与越权测试（A 用户读不到 B 用户数据、非 admin 进不了管理端） |

> **首个管理员如何产生**：由环境变量 `ADMIN_EMAIL` 指定（该邮箱注册后自动置 `role='admin'`），或提供一次性初始化脚本。避免"谁能成为管理员"依赖人工改库。

### 9.1 注册策略（已决策：邀请码 / 白名单）
