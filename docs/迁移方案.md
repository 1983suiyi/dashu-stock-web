# 大数选股工具迁移方案

> 本方案覆盖当前版本升级：指数手动刷新切换为低频自动刷新、增加指数历史/牛熊分析接口，并说明既有浏览器数据向账号云端数据的迁移流程。

## 1. 迁移目标与原则

1. 将上证指数手动刷新迁为每 60 秒自动刷新，同时限制上游行情请求频率。
2. 保留现有 `/api/kline`，让股票评分、股票现价和一年/三年低价流程保持兼容。
3. 新增的指数快照、指数历史路由为增量接口，不改动用户数据数据库表结构。
4. 让既有浏览器中的个人数据可由用户主动导入账号；迁移前保留可恢复的本地数据和数据库备份。
5. 部署时前后端成套升级；出现问题时回滚代码版本，但不删除或覆盖用户数据库。

## 2. 数据范围与迁移映射

### 2.1 用户私有数据

首次登录时，同步层会检查以下浏览器 `localStorage` 数据，并询问是否导入当前账号：

| 浏览器 key | SQLite `user_data.kind` |
| --- | --- |
| `dashu-user-holdings` | `holdings` |
| `dashu-cash-balance` | `cash` |
| `dashu-total-assets` | `totalAssets` |
| `dashu-capital-events` | `capitalEvents` |
| `dashu-workspace-archives` | `archives` |

导入后按 `user_id + kind` 覆盖保存到服务端。登录同步会再从云端拉取数据并写回本地；云端为已存在数据的权威副本。首次迁移完成标记保存在 `dashu-migrated:<userId>`，会话重载保护标记保存在 `sessionStorage`。

**重要：**请在原浏览器配置文件中登录并完成导入。先通过应用导出需要留存的 CSV，并保留原浏览器数据，直到另一设备登录后确认持仓、现金、流水和归档均正确。不要手动删除迁移标记来重复导入，否则可能用旧本地数据覆盖较新的云端数据。

### 2.2 非用户私有数据

- 市场温度是全站公共数据，保存在 SQLite `market_temperature`，不并入某个用户的私有数据。
- 股票池、估值快照、全量 K 线进度和指数当日快照仍以浏览器缓存为主，不随账号数据迁移。
- 指数历史日线、行业周期和个股估值历史的服务端缓存可在部署后重新生成；清空它们不会删除用户持仓。
- 自动刷新和牛熊阶段功能不新增数据库表，也不转换现有评分、归档或持仓数据格式。

## 3. 上线前准备

1. 记录当前 Git commit、部署包和 Node.js 版本，确保可回退到同一份前后端版本。
2. 检查 Node.js `>=22.13`，推荐 Node.js 24 LTS；`node:sqlite` 不适用于旧版 Node。
3. 备份服务端数据库和环境配置：

   ```bash
   npm run backup
   cp .env .env.backup
   ```

   将备份放到安全位置，不要提交 `.env` 或 SQLite 数据库。
4. 若正在从单用户浏览器缓存迁移，记录旧浏览器配置文件并导出必要 CSV；不要先清除 `localStorage`。
5. 检查腾讯行情接口在当前部署环境可以访问。迁移验证使用单次请求，不运行短间隔压力测试。

## 4. 部署步骤

### 4.1 单体部署（当前默认）

前端静态文件和 API 由 `server/index.mjs` 同一进程提供，建议按同一发布包完成：

```bash
npm ci
npm run lint
npm run build
npm start
```

若服务由进程管理器托管，在构建后重启服务进程，让 Node 重新加载新增路由。不要只覆盖 `dist/` 而不重启后端，也不要只更新后端而长期保留旧前端缓存。

### 4.2 分离部署

如果前端静态站点和 API 服务分开发布，顺序应为：

1. 先发布后端 `/api/index-snapshot` 和 `/api/index-history`。
2. 确认后端健康后再发布引用 `/api/index-snapshot` 的前端 bundle。
3. 保留 `/api/kline`；它仍是股票数据流程的必要接口。

这避免新前端请求尚未部署的路由。开发环境 Vite 插件与生产路由都应接入相同的 `server/kline.mjs` 和 `server/index-history.mjs`。

## 5. 验收清单

- [ ] `npm run build` 与 `npm run lint` 通过。
- [ ] 登录、退出、用户持仓/资金读取和写入正常；使用专用测试账号验证数据隔离。
- [ ] 首次登录的旧数据导入提示符合预期，导入后至少检查持仓、现金、流水和归档。
- [ ] 单次访问 `GET /api/index-snapshot?symbol=sh000001` 返回有效报价；无需为验证自动刷新而连续请求上游。
- [ ] 页面显示自动刷新周期 60 秒和最近更新时间；隐藏浏览器标签页时不产生轮询，恢复可见后触发刷新。
- [ ] `/api/kline` 仍能服务个股行情和低点补齐；一次指数刷新不触发该历史 K 线流程。
- [ ] `/api/index-history?symbol=sh000001&years=20` 返回历史日线；页面可显示阶段、转折和顶底 K 线。
- [ ] 管理端鉴权、管理员角色限制和公共市场温度读取正常。

当前刷新保护：前端每个可见页面至多每分钟请求一次，隐藏时暂停；服务端单进程有 30 秒报价缓存和同标的并发合并。多进程部署时缓存不跨进程共享，应结合实例数量和上游配额重新评估刷新频率。

## 6. 观察与调参

- 观察 `/api/index-snapshot` 的请求数、响应时间、超时和非 2xx 比例。
- 多用户部署应按服务进程数评估上游总请求量；30 秒内缓存和并发合并仅作用于同一 Node 进程。
- 若出现超时、限流或报价源不稳定，可将 `src/App.tsx` 中 `INDEX_REFRESH_INTERVAL_MS` 调大到 `120_000` 或 `300_000`，重新构建并发布。
- 若行情长时间不变，先确认是否为非交易时段、上游数据未更新或缓存命中，不应通过提高轮询频率来强行制造更实时的行情。
- 前端请求失败时应保留最后一次有效点位；排查期间不要清理用户缓存或数据库。

## 7. 回滚方案

### 7.1 指数功能回滚

1. 先回滚前端到使用手动刷新或原快照调用的上一版本。
2. 再按该版本匹配回滚服务端；若只回滚前端，可保留新增的 `/api/index-snapshot` 路由，它不影响 `/api/kline`。
3. 若新前端仍在使用而后端已回滚到不支持 `/api/index-snapshot` 的版本，快照更新会失败；因此前后端需要成套回滚或先恢复该兼容路由。
4. 自动刷新间隔是前端构建常量，临时降频需要修改常量、重新构建并发布；不存在运行时环境变量开关。

### 7.2 用户数据回滚与恢复

- 不因前端问题删除 `server/dashu.db`、`server/backups/` 或用户本地存储。
- 如数据库文件损坏，先停止服务并复制保留当前数据库，再从最近一次备份恢复；不要在运行中的 SQLite 数据库上手工覆盖文件。
- 回滚旧版前端不会删除 SQLite 中已导入的用户数据；升级回新版本后仍可按账号读取。
- 账号导入结果异常时，暂停继续导入，保留原浏览器配置文件与数据库备份，再逐账号核对；不要批量重置迁移标记。

## 8. 迁移完成标准

- 新版前端和后端版本匹配，API 与页面验收项通过。
- 旧浏览器中的个人数据已完成一次导入，并在另一浏览器或设备验证账号同步。
- 自动刷新以 60 秒运行，浏览器后台暂停；上游请求量和错误率在可接受范围内。
- 数据库、环境变量和发布回滚包均有独立备份，维护人员知道恢复路径。
